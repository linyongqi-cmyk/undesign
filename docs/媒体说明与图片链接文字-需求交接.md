## 2. 背景与核心目标

项目为 Astro 静态作品集，本地管理页使用 React/Puck 编辑画布。媒体可能独立出现，也可能位于内容组、布局群组、自由尺寸群组以及图文分栏中。

此前本地视频与在线视频说明使用不同的编辑实现，出现过输入框被画布交互层挡住、说明区带灰底等问题。用户明确强调：本次功能必须具有统一性，所有媒体组件的说明应使用同一套能力，不能逐个组件复制实现后各自发展。

本次两个目标：

1. 为所有媒体组件提供可设置的外部文字说明，可选媒体上方或下方，并可设置与媒体的间距。
2. 为图片提供位于内部右下角的超链接文字；图片悬停放大时，文字随图片等比例放大，放大状态也能点击跳转。

两者是不同用途，应有独立字段及编辑入口，不要复用一个 caption 字段在两种位置之间切换。两者允许同时存在是本文建议，需确认。

## 3. 已明确的需求

### 3.1 所有媒体的外部文字说明

- 所有媒体组件都应有添加文字说明的选项。
- 说明显示在所属媒体的外部。
- 可以选择在媒体上方或下方。
- 可以设置文字与所属媒体之间的间距。
- 参考现有视频说明，但不能延续本地视频和在线视频各写一套的方式。
- 管理画布与前台对同一份内容，应有一致的文字、位置和间距。

### 3.2 图片内部的链接文字

- 是可编辑的文字内容，并关联一个可点击跳转的链接。
- 显示在图片内部右下角。
- 图片开启悬停放大后，文字须随图片等比例放大。
- 放大后的文字仍可点击跳转。
- 原请求“文字内部的右下角”根据上下文按“图片内部右下角”理解；实施前应让用户确认此理解。

### 3.3 统一性是验收要求

- 独立媒体与群组内同类型媒体具有相同设置能力。
- 不因页面模板或群组类型不同而换一套默认说明样式。
- 相同字段、默认值、数值单位、校验及编辑交互必须一致。
- 前台与管理页可使用不同框架外壳，但必须共享数据规范、归一化规则和样式；不能分别定义业务规则。
- 不将文字画进图片文件，文字应保留为可编辑的数据及真实网页文字。

## 5. 推荐的实现方向

### 5.1 方案比较

1. **推荐：统一数据与行为，适配现有 Astro/React 渲染路径。** 共用说明字段、默认值、校验、CSS 和编辑表单；各渲染器调用共享逻辑，只保留框架相关的薄外壳。能兼容现有页面及旧内容，避免大范围重构。
2. 为此重写所有媒体为一个大型组件。统一程度高，但会牵动裁切、群组布局、轮播、视频及悬停逻辑，不适合作为本次默认方案。
3. 给每类组件分别加字段和表单。初期改动小，但会重现已发生的不一致，不符合用户目标。

上述推荐尚未由用户正式选定。不要引入新的框架或第三方富文本依赖。

### 5.2 建议的数据规范（字段名仅作示意）

```ts
type MediaCaption = {
  text: string;
  position: 'top' | 'bottom';
  gap: number; // px，有限且非负；范围需统一定义
};

type ImageLinkLabel = {
  text: string;
  href: string;
  newTab: boolean;
};
```

- 建议说明为空时不渲染，也不保留空白间距。
- 建议说明默认下方，默认间距沿用当前视频约 8px；这是建议，不是已确认要求。
- 若提供启用开关，关闭不能清空原文字；应区分“隐藏”和“删除内容”。
- 建议链接文字与 URL 都有效才渲染可点击链接，表单应明确提示缺失/无效输入。
- 只保存最小必要字段，默认值在共享归一化函数中定义。
- 链接标签属于图片数据，外部说明属于被确认的媒体项/容器；不要复制到互相冲突的多个位置。
- 若决定保留 `caption: string` 并增设配置对象，也可接受，但必须统一访问层，不可多处各自解析新旧数据。

### 5.3 旧内容兼容

- 现有图片和视频已有 `caption?: string`。新增对象字段时不能直接假设旧 caption 已是对象。
- 建议统一读取层把旧字符串转换为下方说明和默认间距，新格式优先；明确两者同时存在时的优先级。
- 不打开页面就批量重写全站作品 JSON；优先按读取兼容、用户保存后规范化的方式处理。
- 所有 Puck 转换、嵌套媒体转换、保存接口校验都要传递新字段。
- 检查移动组件、组合/解散群组、切换模板、复制已有内容等操作是否保留说明及链接。
- 不得将 `dist/`、截图、浏览器 DOM 或生成预览当作作品数据源。

## 6. 布局与视觉规则

### 6.1 外部说明

建议拆分为三个概念：媒体排版单元、实际媒体视口、外部说明。说明与媒体视口按上下顺序排版。

- 说明不覆盖图片、视频或在线视频控制栏。
- 说明使用透明背景，不继承视频占位底色，不无故增加边框或卡片样式。
- 间距仅作用在说明与所属媒体之间；不要修改整个群组的组件间距。
- 文字换行后不能溢出所属媒体宽度，长 URL/长单词也不能撑破排版。
- 群组仍保持既有零组件间距规则；说明属于媒体项内部占用空间。
- 说明新增高度不能被误当成图片的宽高比。尤其检查固定高度横排、等高媒体行、自由尺寸组和超宽排版。
- 需要明确：等高是媒体视口等高，还是包含说明的整体等高；建议保持媒体视口等高，让说明位于其外。
- 手机保持同样的位置及 px 间距规则，除非最终设计明确另外设置。

### 6.2 图片内部链接

- 链接相对于“最终可见图片视口”定位在右下角，不相对于图片自然尺寸或整篇文章定位。
- 图片裁切/平移/缩放时，标签仍固定于可见视口右下角；不要跟着裁切源图移出视口。
- 图片悬停放大时，视口画面与标签组成一个整体放大；文字字号、内边距及其他视觉尺寸使用同一倍率。
- 这意味着裁切变换与悬停变换应分层处理：裁切影响图像，悬停影响图像视口与标签整体。
- 只把文字设为链接，不能擅自把整张图片变成链接。
- 外部说明不跟随图片进入放大层（建议行为，待确认）。
- 保持现有极简视觉；链接默认颜色、字号、内边距及是否有轻背景需确认，优先保证图片上可读。

## 7. 悬停放大与链接事件：重点风险

当前 `src/lib/content/image-hover-preview.js` 的实现会在 body 创建 fixed 放大层，只新建一个 img；放大层有 `pointer-events: none`、`aria-hidden="true"`，并在捕获阶段 pointerdown 关闭、click 中阻止默认行为。

所以“给原图加一个 a 标签”并不足以完成需求。接手 AI 必须重新梳理：

1. 放大层如何同步图片链接文字、视觉样式和同一倍率，而不是只复制 img。
2. 放大层链接如何接收指针事件，并正确跳转。
3. pointerdown 捕获关闭逻辑是否会在链接 click 前移除 DOM。
4. layer 的 click preventDefault 是否错误阻止链接跳转。
5. 缩回动画、滚动/resize/Esc 关闭、离开页面的清理是否仍正确。
6. 放大区域遮住相邻图片时，不应触发底层图片或错误切换目标。
7. 链接点击是否与群组进入编辑、拖拽、裁切、悬停预览等交互冲突。
8. 放大层若含可操作链接，不能将该交互内容错误地藏在 aria-hidden 子树中；同时避免重复 Tab 焦点。

保留原有放大约束：普通图片才可开启，倍率 1.1–2.5、左/中/右基点、视口边缘避让、触屏和手机不启用、无新增阴影。不要借本次改动擅自给轮播或视频加放大功能。

推荐把需要共享的标签结构/数据提取为可复用逻辑，避免 Astro 原图、React 预览和 JS 放大副本各写一套样式。

## 8. 管理页编辑与保存

- 外部说明使用同一个编辑表单组件，所有适用媒体调用；图标名称、字段次序、默认值和错误提示一致。
- 建议入口名为“文字说明”，字段至少为文字、上方/下方、间距(px)。图片另有“图片链接文字”入口。
- 不把视频的 iframe 内置字幕（CC）与媒体外部说明混淆。
- 按钮放在内容外右侧，不占用媒体和说明本身宽度；群组操作与子组件操作保持现有选择层级。
- 所有表单/按钮必须按现有 `registerOverlayPortal` 模式处理画布交互层，否则会再次出现“看得见但不能编辑”。
- 管理画布编辑时点击链接不应误跳站；前台链接正常跳转。设置中的放大预览是否可跳转需明确，并提供可靠关闭方式。
- 与现有撤回/重做及草稿保存机制一致，不绕开统一历史直接写文件。
- 若采用“应用”表单：未应用输入属于表单本地状态，应用一次为一个页面历史步骤；若采用实时编辑则沿用现有字段输入记录规则。两种媒体不能各用不同约定。
- 保存、刷新、切换作品后新字段仍保留。不要只做到 React 临时状态可见。

## 9. 链接安全与可访问性

- 使用真实 a 元素，具有清楚的链接文字、键盘焦点及 Enter 激活能力。
- 不直接使用 dangerouslySetInnerHTML 渲染用户文字；普通说明/标签先按纯文本处理。
- 延用项目 URL 校验；禁止 javascript:、data: 等协议。站内链接若纳入范围，复用现有路径生成，不另造硬编码规则。
- 新标签站外链接设置合适的 rel（如 noopener noreferrer）。
- 保留图片 alt，说明和链接标签不能取代 alt。
- 链接放大前后保持同一地址和打开方式，不发生一次点击打开两次。
