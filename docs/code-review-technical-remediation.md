## 每批执行与验收顺序

1. **先记基线。** 构建当前代码，确认要改的入口和使用它的真实作品。记录路由、作品区块顺序、浏览器操作结果。涉及保存和数据错误样例时使用隔离副本，先保留原内容与媒体清单。
2. **跑当前批的最小检查。** 第一批先验证旧标记是否存在与类型覆盖。数据校验批先看当前目录全量基线，再在副本用正反例验证。性能和无障碍批先采集能复现的症状。
3. **实施一个可单独撤销的改动。** 先处理本批最小问题。独立的样式、数据迁移、类型检查门槛和编辑器拆分分别保留验证与回退边界。
4. **运行构建和本批定向检查。** 根路径执行 `npm run build`，涉及导航、媒体路径、详情模板或构建校验时，再用 `SITE_URL=https://example.github.io BASE_PATH=/linyongqi-homepage/ npm run build -- --outDir <临时目录>`。确认两套构建的页面数量、sitemap 和媒体路径。建立类型入口后执行 `npm run check`。需要锁住具体回归时，可定向使用现有 `scripts/local-admin-storage.test.mjs`、`scripts/puck-work-document.test.mjs` 或 `scripts/photography-lightbox-viewer.test.mjs`，仅运行与本批相关的检查。
5. **打开正常入口验收。** 改服务端管理模块先重启 Astro，确认真实 API 响应。以同一已保存作品同步检查管理画布与前台，重点看内容、顺序、样式、布局和编辑辅助控件的位置。测试保存后刷新重载，确认作品状态一致。浏览器或真实设备未检查的项目如实记为未验证。
6. **写交接和修改记录。** 纯类型、清理和文档按实际可见行为判断版本。前台可见修复与管理流程修复各递增对应 PATCH，新增能力按对应 MINOR，兼容性破坏按对应 MAJOR。记录两个版本、实际检查、未验证事项和发布状态。此次只交付方案，发布须按仓库流程另行授权。
